# news-pilot

Агент ведения новостного Telegram-канала: демон опрашивает RSS-ленты, догружает полные тексты статей,
дедуплицирует новости против опубликованных постов (эмбеддинги + LLM-вердикт, параллельно), затем раз в
N минут батч-отбор: все накопившиеся уникальные новости идут в один LLM-вызов, модель выбирает одну —
она проходит фото-агента, поиск контекста и генерацию поста в стиле канала (с ответом на прошлый пост при
развитии истории) и публикуется в Telegram.

HTTP-сервера в приложении нет: источник — RSS, мониторинг — логи и админ-меню бота.

## Архитектура в двух словах

- **Пайплайн целиком в памяти**: две очереди новостей (`FeedItem`) и очередь постов (`PublishJob`) —
  `asyncio.Queue` с толстыми объектами; промежуточных статусов в БД нет.
- **БД — 2 таблицы**: `posts` (только опубликованные посты + эмбеддинги, pgvector) и `counters`
  (накопительные счётчики: дубликаты, отбор, ошибки, clear-run). Схема создаётся автоматически.
- **Поток**: poller кладёт `FeedItem` в очередь 1 → X параллельных дедуп-воркеров (семафор
  `pipeline.concurrency`) гонят каждый свой эмбеддинг → pgvector-поиск по опубликованным постам →
  один LLM-вызов решает только «дубликат/не дубликат» → уникальная новость копится в очереди 2.
  Раз в `pipeline.batch_interval_seconds` очередь 2 выгребается под 0: весь батч идёт в один
  LLM-вызов, модель выбирает одну новость (или «ничего не публиковать»), невыбранные отбрасываются.
  Выбранная проходит фото-агент, поиск контекста, генерацию, и `PublishJob` уходит в очередь
  постинга → один асинхронный отправитель публикует в Telegram и записывает пост с эмбеддингом
  в `posts`. Параллелится только дедуп; отбор и запись — строго последовательно.
- **Ограничения**: дедуп — только против опубликованных постов; невыбранная на отборе новость
  забывается навсегда, её перефразированный дубликат из другой ленты может позже пройти дедуп и
  выиграть свой батч. Черновики модерации, очереди и незавершённая работа живут в памяти
  и умирают при рестарте.

## Возможности

- Опрос произвольного числа RSS-лент по расписанию (`rss.poll_interval_seconds`).
- Догрузка полного текста статьи по ссылке (trafilatura, fallback на summary из ленты).
- Дедупликация (единственная параллельная фаза): векторный поиск ближайших опубликованных постов
  (pgvector) + LLM-вердикт только «дубликат/не дубликат»; X параллельных воркеров
  (`pipeline.concurrency`).
- Батч-отбор: раз в `pipeline.batch_interval_seconds` очередь уникальных новостей выгребается под 0,
  весь батч идёт в один LLM-вызов с контекстом публикации (время, свежесть последнего поста),
  модель выбирает одну самую значимую новость; невыбранные отбрасываются (счётчик `not_selected`).
  Темп публикации задаётся самим интервалом отбора: не больше одного поста за тик.
- Подбор фото: Tavily-поиск картинок + vision-оценка кандидатов LLM (0–4 фото на пост, с контентными ограничениями — см. `app/photo/agent.py`).
- Поиск связанных прошлых постов канала (продолжения истории публикуются ответом на прошлый пост) по эмбеддингам.
- Генерация поста в стиле канала (HTML, ≤1000 символов по умолчанию — `generator.max_length`) — стиль и контентные правила задаются в `prompts/style.md`:
  без отсылок к СМИ, без призывов в комментарии, нейтральная подача без оценочных формулировок в отношении
  России/российских властей, без оборотов «как мы писали ранее».
- Публикация: сразу в канал (`auto`) или через модерацию админом (`moderation`).
- Админ-бот: инлайн-статистика из `posts` + `counters`, модерация черновиков, уведомления о публикациях.
- Независимые прокси (socks5/http) для каждого компонента: rss, llm, embeddings, photos, publish, telegram.
- Очереди не персистентны: при рестарте незавершённая работа (новости в очереди дедупа, уникальные
  новости в очереди отбора, посты в очереди публикации, черновики модерации) теряется — это осознанное
  упрощение, состояние пайплайна живёт в памяти; в БД хранятся только опубликованные посты и счётчики.

## Стек

Python 3.12, feedparser, trafilatura, PostgreSQL 16+ с pgvector (на хост-машине), asyncpg (raw SQL),
OpenAI-compatible LLM (openai SDK), Ollama (эмбеддинги), tavily-python, aiogram 3, pydantic-settings.

## 1. Установка

### Вариант A — локально (для разработки)

```bash
# 1) Виртуальное окружение и зависимости
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt

# 2) Файлы конфигурации
cp .env.example .env               # заполнить секреты (см. раздел «Конфигурация»)
cp config.example.yaml config.yaml # настроить фиды/канал/режим
```

#### PostgreSQL + pgvector (Debian/Ubuntu)

```bash
sudo apt install postgresql
# пакет pgvector: имя зависит от версии PG, например postgresql-16-pgvector
sudo apt install postgresql-16-pgvector

# роль и база — любые; всё это прописывается в .env (DATABASE__DSN)
sudo -u postgres psql -c "CREATE ROLE мой_юзер LOGIN PASSWORD 'мой_пароль';"
sudo -u postgres createdb -O мой_юзер моя_база
```

Расширение `vector` включается автоматически при первом старте приложения
(`app/db/schema.sql` выполняет `CREATE EXTENSION IF NOT EXISTS vector;`).
Схема БД тоже создаётся автоматически (`CREATE ... IF NOT EXISTS`), старая схема
(таблицы `news`, старый `posts`, `post_images`, `post_references`, `processing_log`)
дропается при первом старте с новой версией — данные не переносятся.

В `.env` указать (юзер/пароль/база — ваши):

```
DATABASE__DSN=postgresql+asyncpg://мой_юзер:мой_пароль@localhost:5432/моя_база
TEST_DSN=postgresql+asyncpg://мой_юзер:мой_пароль@localhost:5432/моя_база_test
```

#### Ollama (эмбеддинги)

```bash
curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen3-embedding:0.6b   # модель по умолчанию: 1024 dims, ~1 ГБ RAM
```

#### Запуск

```bash
.venv/bin/python main.py
```

### Вариант B — Docker

PostgreSQL в compose **нет** — требуется работающий PostgreSQL на хост-машине
(прослушивает localhost, юзер/база — из `DATABASE__DSN`).

```bash
cp .env.example .env && cp config.example.yaml config.yaml  # заполнить
docker compose up -d --build                  # app (БД — на хосте)
docker compose --profile optional up -d ollama  # если нужен локальный Ollama (том ollama персистентен)
```

Из контейнера БД доступна по `host.docker.internal:5432` (в compose добавлен `host-gateway`),
поэтому в `.env`: `DATABASE__DSN=postgresql+asyncpg://юзер:пароль@host.docker.internal:5432/база`.

PostgreSQL должен слушать TCP (в `postgresql.conf` `listen_addresses = 'localhost'` — достаточно).
Для доступа из контейнера на Linux добавьте правило в `pg_hba.conf` для docker-моста,
например: `host all all 172.16.0.0/12 scram-sha-256`, затем `sudo systemctl reload postgresql`.

В контейнере монтируются только `app/`, `prompts/`, `main.py` (образ) и `config.yaml:ro` (том);
`.env` передаётся через `env_file`. Файлы на диск не пишутся (фото живут в памяти).

## 2. Конфигурация

### Источники и приоритет

Параметры складываются в объект `Settings` (`app/config.py`) из четырёх источников
(выше в списке = выше приоритет):

1. **Переменные окружения** (реальный `export VAR=...`);
2. **`.env`** (путь переопределяется переменной `ENV_FILE`);
3. **YAML-файл** (путь: переменная `CONFIG`, иначе строка `CONFIG=...` в `.env`, иначе `config.yaml` в корне);
4. **Значения по умолчанию** из кода (`app/config.py`).

Вложенность YAML в env — через `__`: `llm.temperature` → `LLM__TEMPERATURE`,
`telegram.bot_token` → `TELEGRAM__BOT_TOKEN` и т.д. **Любой** параметр YAML можно переопределить
переменной окружения. Неизвестные ключи в YAML/.env запрещены (`extra=forbid`) — опечатка упадёт с явной ошибкой.

### Telegram: подготовка

1. **Бот**: @BotFather → `/newbot` → токен в `TELEGRAM__BOT_TOKEN`.
2. **Канал**: добавить бота **администратором** канала с правом «Публикация сообщений»;
   `telegram.channel_id` — `@username` публичного канала или числовой id (`-100...`).
3. **admin_id**: свой Telegram user id (узнать можно у @userinfobot) → `telegram.admin_id`.
   Апдейты от остальных пользователей игнорируются.

### Режимы публикации

- `publish.mode: auto` — пост уходит в канал сразу; с `notify_admin: true` админ получает
  уведомление (ссылка на пост, источник, возраст новости).
- `publish.mode: moderation` — черновик приходит админу в личку: «Опубликовать», «Без фото»
  (если фото есть), «Редактировать» (прислать новый текст), «Отклонить». Неотвеченный черновик
  через `moderation_timeout_hours` отклоняется автоматически.
- Смена режима — только правка конфига + рестарт, код менять не нужно.

### Батч-отбор и темп публикации

Темп задаётся самим `pipeline.batch_interval_seconds`: за тик публикуется не больше одного поста —
жёсткого дневного лимита нет. Раз в интервал очередь уникальных новостей выгребается под 0, весь
батч идёт в один LLM-вызов. В промпт передаётся контекст публикации — текущее время и когда вышел
последний пост (сколько минут/часов назад). Модель выбирает ровно одну новость (или отвечает
«ничего не публиковать») — невыбранные отбрасываются навсегда (счётчик `not_selected`). Промпт
инструктирует балансировать частоту по свежести последнего поста и публиковать равномерно
в течение дня: пост только что — выбирать только действительно значимое, постов давно не было —
можно и умеренно значимое.

Невыбранные новости нигде не запоминаются (нет таблицы статусов): посты не создаются, счётчики растут.

### Clear-запуск

`rss.clear_run: true` — при старте все записи, уже лежащие в лентах, добавляются в seen-set poller'а
и не обрабатываются (счётчик `cleared`); публикуются только новости, появившиеся в лентах **после**
запуска. Защита от флуда старыми новостями после простоя. Счётчик виден в `/admin`.

### Стиль канала

`prompts/style.md` — редактируемый стайл-гайд: правила заголовков, тон, эмодзи, формат продолжений
историй. Используется при генерации каждого поста. Помимо стиля, в нём зафиксированы контентные правила:

- продолжение истории — ответом на прошлый пост, без оборотов «как мы писали ранее» / «ранее мы сообщали»;
- без упоминания названий СМИ («по данным», «как сообщает…»), если новость передаётся без них;
- финал поста без призывов писать комментарии (комментарии отключены);
- нейтральная подача: факты, заявления и решения — да; негативные/обвинительные/провокационные
  интерпретации в отношении Путина, России, российского правительства, госорганов, законов, СВО
  и действий российских властей — нет.

Аналогичные контентные ограничения для фото-агента (запрет украинской символики и украинских СМИ,
кроме случаев, когда они необходимы для понимания новости) — в системном промпте `app/photo/agent.py`.

## Пайплайн

```
RSS feeds → Poller → [rss.clear_run: при старте всё, что уже в лентах, → счётчик cleared, конец]
  → догрузка полного текста (trafilatura, fallback на summary)
  → FeedItem в очередь 1 (толстый объект, всё в атрибутах)
  → X параллельных дедуп-воркеров (семафор pipeline.concurrency; единственный параллелизм):
      [1] Дедуп: эмбеддинг (Ollama, вычисляется один раз) → pgvector top-K опубликованных постов
          за window_days с порогом min_similarity → один LLM-вызов: дубликат или нет
        → duplicate → счётчик duplicates, конец
        → unique → FeedItem (+эмбеддинг) в очередь 2
  → раз в pipeline.batch_interval_seconds — цикл батч-отбора (строго последовательно):
      [1] Очередь 2 выгребается под 0 (весь накопленный батч)
      [2] Один LLM-вызов для всего батча: контекст публикации (время, свежесть последнего поста)
          + нумерованный список новостей → модель выбирает одну
        → null (ничего не достойно) → весь батч в счётчик not_selected, конец
        → невыбранные → счётчик not_selected, отбрасываются навсегда
      [3] Выбранная новость — фазы записи по очереди:
          фото-агент: tavily_image_search / inspect_image (vision) / select_images,
              лимиты max_iterations/max_searches/max_images; 0 фото — валидный исход; сбой не блокирует пост
          поиск релевантных опубликованных постов (top-3, context.window_days) по эмбеддингу из дедупа;
              продолжение истории публикуется ответом на прошлый пост, без оборотов «как мы писали ранее»
          генерация поста по prompts/style.md (structured output, ≤generator.max_length символов, HTML;
              без отсылок к СМИ, без призывов в комментарии, нейтральная подача)
          → PublishJob (текст, фото, reply-цель) в очередь постинга
  → 1 асинхронный отправитель: отправка в канал (или черновик админу в режиме moderation),
      эмбеддинг текста → пост сохраняется в таблицу posts
```

Сбой этапа записи не роняет пайплайн: запись повторяется с начала (`pipeline.retries` попыток);
после исчерпания — счётчик `failed`. Ошибка LLM-отбора возвращает весь батч в очередь 2 (ретрай
на следующем тике). Промежуточные статусы не пишутся: исход новости — либо пост в канале (строка
в `posts`), либо инкремент счётчика. Сбой фото/Tavily не блокирует публикацию.

## Счётчики и жизненный цикл

Единственный персистентный результат — опубликованный пост (строка в `posts` + эмбеддинг).
Все остальные исходы накапливаются в таблице `counters` (ключ → значение, атомарный инкремент):

| Ключ | Значение |
|---|---|
| `duplicates` | новость признана дубликатом опубликованного поста |
| `not_selected` | модель не выбрала новость при батч-отборе (или выбрала «ничего») |
| `failed` | ошибка этапа записи после ретраев / слишком короткий текст / сбой публикации / дедуп с `on_error: drop` при ошибке LLM |
| `cleared` | запись была в ленте на момент запуска с `rss.clear_run` |
| `rejected` | черновик отклонён админом или по таймауту модерации |

Компромисс: дедуп смотрит только на опубликованные посты, а невыбранная на отборе новость забывается
навсегда — её перефразированный дубликат из другой ленты не считается дубликатом и может позже
выиграть свой батч.

Фото нигде не persist'ятся: байты живут в памяти от выбора фото агентом до публикации. Черновики
модерации тоже в памяти: кнопки в чате админа работают, пока процесс жив; после рестарта кнопки
отвечают «черновик утерян». Незавершённая работа при рестарте просто теряется (без записи в БД).

## Бот

- Один админ: `telegram.admin_id`. Апдейты от остальных игнорируются.
- `/admin` — статистика канала: опубликованные посты (24ч/7д/всего) из `posts`,
  накопительные счётчики из `counters`, очереди дедупа/отбора в памяти,
  черновики и очередь публикации, источники за 24ч.
- Модерация: черновик приходит в личку админу; кнопки «Опубликовать», «Без фото»
  (если есть фото), «Редактировать» (прислать новый текст), «Отклонить». Таймаут
  (`publish.moderation_timeout_hours`, 24ч) → отклонение. Черновики в памяти:
  после рестарта кнопки отвечают «черновик утерян».
- В режиме `auto` с `publish.notify_admin: true` после каждой публикации админу приходит
  уведомление: ссылка на пост, источник и возраст новости.

## Устранение неполадок

| Симптом | Причина / решение |
|---|---|
| `extension "vector" is not available` | не установлен пакет pgvector (`postgresql-16-pgvector` и т.п.), переустановить и пересоздать БД |
| Ошибка подключения к БД | проверить `DATABASE__DSN`; из Docker — `host.docker.internal` вместо `localhost` и правило в `pg_hba.conf` |
| Размерность вектора не совпадает | `embeddings.dimensions` зашита в схему; вернуть 1024 или пересоздать базу |
| `telegram.bot_token is missing` | не заполнен `TELEGRAM__BOT_TOKEN` в `.env` |
| Посты не приходят в канал | бот не админ канала или нет права публикации; проверить `channel_id` |
| `cleared` сразу после старта | это `rss.clear_run: true` — старые записи пропускаются сознательно |
| 403 при скачивании фото | часть CDN требует браузерные заголовки (уже зашиты в `main.py`); поможет `photo_agent.proxy` |
| Эмбеддинги падают | Ollama не запущена или модель не скачана (`ollama pull qwen3-embedding:0.6b`) |
| `llama-server process no longer running` / внезапные 400 от `/api/embed` | OOM-killer убил llama-server: слишком много параллельных embed'ов для серверной RAM. Поставьте в compose для ollama `OLLAMA_NUM_PARALLEL: "1"`, `OLLAMA_CONTEXT_LENGTH: "2048"`, `OLLAMA_KEEP_ALIVE: "-1"` и уменьшите `pipeline.concurrency` (4) и `embeddings.max_chars` (3000); проверить: `dmesg -T \| grep -i oom` |
