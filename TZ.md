# ТЗ: Агент ведения новостного Telegram-канала (news-pilot)

## 1. Цель

Сервис-демон, который сам опрашивает список RSS-лент новостных сайтов, догружает полный текст статьи по ссылке, фильтрует дубликаты через векторный поиск + LLM, подбирает к новости фотографии через ИИ-агента с инструментами, генерирует пост в стиле живого админа канала (со ссылками на прошлые посты, если это развитие истории) и публикует его в Telegram-канал. HTTP-сервера нет: источник новостей — RSS, мониторинг — по логам.

## 2. Стек

- **Python 3.12**
- **feedparser** — парсинг RSS-лент
- **trafilatura** — извлечение полного текста статьи из HTML по ссылке
- **PostgreSQL 16+ + pgvector** (устанавливается на хост-машине, НЕ в docker) — хранение новостей, постов, векторов
- **asyncpg** — асинхронный доступ к БД (raw SQL; схема создаётся при старте, `app/db/schema.sql`)
- **openai** (Python SDK, `base_url` в конфиге) — LLM, OpenAI-compatible API: structured output (json_schema с авто-fallback на json_object), tool-calling, vision-вход. Проверено: `glm-5.3-flash` (OpenCode Go / OpenRouter, ~$0.15/$0.50 за 1M токенов, vision + tools, 2–5 с на пост). Бесплатные модели OpenRouter для прод не годятся — 3–8 мин на генерацию.
- **Ollama** — эмбеддинги (локально, отдельный провайдер от LLM). Проверено: Qwen3-Embedding 0.6B/4B/8B в квантизации Q4_K_M; рекомендуется **0.6B (1024 dims)** — качество ранжирования то же, RAM ~1 ГБ, 33 мс/embed на RTX 4070 (CPU-режим 2 ядра: ~0.5 с).
- **tavily-python** — поиск фото (в песочнице `page_test/` есть безключевой shim Bing/Openverse с тем же интерфейсом)
- **aiogram 3.x** — публикация и модерация в Telegram
- **pydantic-settings** — конфигурация
- **pytest + pytest-asyncio** — тесты
- Docker + docker-compose — развёртывание (только `app` + optional `ollama`; PostgreSQL — на хост-машине, в compose не входит)

Ключевое архитектурное требование: **LLM-провайдер и Embedding-провайдер — две независимые абстракции** (`LLMProvider`, `EmbeddingProvider`) с отдельными конфигами. LLM — OpenAI-compatible (может быть OpenAI, прокси, vLLM и т.д.), эмбеддинги — Ollama. Меняются независимо друг от друга. Модель данных привязана к `embeddings.dimensions` (см. п. 12): смена модели эмбеддингов требует пере-эмбеддинга корпуса и миграции схемы.

## 3. Пайплайн обработки новости

```
RSS feeds → Poller (интервал) → новая запись → догрузка полного текста (trafilatura)
  → сохранение → эмбеддинг
  → [1] Дедупликация (pgvector top-5 + LLM-вердикт)
      → дубликат → status=duplicate, конец
      → уникальная → [2] Фото-агент (Tavily + vision)
      → [3] Поиск релевантных постов в БД постов
      → [4] Генерация текста поста (LLM)
      → [5] Публикация (auto | moderation)
      → сохранение поста + его эмбеддинга в БД постов
```

Обработка асинхронная, но последовательная: poller кладёт найденные новости во внутреннюю очередь (asyncio.Queue) и сразу продолжает опрос фидов; pipeline-цикл разбирает очередь по одной новости за раз.

## 4. RSS-сборщик

- Конфиг `rss.feeds`: список `{name, url}`. Опрос каждые `rss.poll_interval_seconds` (дефолт 300 сек), все фиды параллельно (asyncio).
- Из записи фида берём: `title`, `summary`, `link`, `guid`, `published`. Вложенные картинки (enclosures/media:content) **игнорируются** — фото всегда ищет фото-агент через Tavily (см. п. 6).
- Идемпотентность: `external_id = guid` записи (если нет — нормализованный `link`); Unique(source, external_id), уже виденные записи пропускаются до обработки.
- Догрузка полного текста: trafilatura по `link` (таймаут `fetcher.timeout_seconds`, дефолт 30с, ретраи `fetcher.retries`, дефолт 2). Не удалось → fallback на `summary` из фида (`full_text_fetched=false`).
- Если итоговый текст < мин. длины (дефолт 100 символов) → `status=failed`, в пайплайн не идёт.
- Упавший/невалидный фид → ошибка в лог, остальные фиды работают независимо.

## 5. Модуль дедупликации

0. **Одна новость = один эмбеддинг, чанкование не применяется.** Задача — document-level similarity, а не фрагментный поиск; новости короткие (500–5000 символов), в контекст модели влезают целиком; векторный поиск — лишь грубый фильтр кандидатов (финальное решение принимает LLM); чанкование дало бы ложные срабатывания на одинаковых фоновых абзацах. Вход для эмбеддинга: `title + text[:embeddings.max_chars]` (дефолт 6000 символов); модель эмбеддингов должна иметь контекст ≥ этого объёма.
1. Текст новости (title + text, по правилу п. 0) → эмбеддинг через `EmbeddingProvider` → сохранение в pgvector.
2. Поиск top-5 ближайших новостей (cosine distance) среди новостей за последние **X дней** (конфиг `dedup.window_days`, дефолт 3) с порогом сходства (конфиг `dedup.min_similarity`, дефолт 0.75). Если кандидатов нет — новость уникальна, LLM не вызывается.
3. Если кандидаты есть — LLM получает: новую новость + до 5 похожих (текст + дата) и отвечает **строго в structured output** (JSON Schema / response_format):

```json
{
  "is_duplicate": true,
  "reason": "та же новость, переформулирована",
  "duplicate_of_id": 123
}
```

4. Дубликат → `status=duplicate`, сохраняем связь с оригиналом, пайплайн завершается.
5. При ошибке/таймауте LLM: 3 ретрая с backoff; при финальной ошибке — новость **не отбрасывается**, уходит в `status=needs_review` (fail-open с меткой), поведение настраивается (`dedup.on_error: review | pass | drop`).

## 6. Фото-агент

Полноценный агент на tool-calling loop (макс. итераций — конфиг, дефолт 10). Модель — та же LLM с vision и tool-calling (проверено на `glm-5.3-flash`).

**Инструменты:**

- `tavily_image_search(query: str)` → список URL изображений (tavily, `include_images=true`).
- `inspect_image(url: str)` → скачивает изображение, возвращает его модели как image input → модель оценивает релевантность, качество, отсутствие водяных знаков/текстового спама.
- `select_images(ids: list[str])` → финальный выбор 1–4 фото, завершение цикла.

**Правила:**

- Промпт: суть новости, требования (без NSFW, без логотипов СМИ/водяных знаков, горизонтальные предпочтительны).
- **Иерархия выбора**: лучший вариант — кадр, напрямую связанный с сутью новости (участники, место, предмет). Если точных кадров нет — подбирается **тематически близкое фото** (тот же объект, тема, окружение события). Пустой `select_images` — крайний случай: только если и тематические кандидаты не подходят (пост без фото хуже, чем пост с уместным тематическим кадром).
- **Постепенное обобщение запросов**: начинать с точных запросов; при неудаче расширять (тема → объект → место), а не отказываться сразу.
- Вложенные картинки из RSS-записи (enclosures/media:content) агенту **не передаются** — агент всегда начинает с поиска в Tavily.
- Агент обязан делать не более N поисковых запросов (конфиг, дефолт 5).
- Выбранные фото скачиваются локально (с ретраями), проверяется размер/формат (jpg/png/webp, ≤10 МБ), невалидные отбрасываются; если после этого 0 фото — текстовый пост.
- URL и локальные пути фото сохраняются в БД.
- Качество поиска фото зависит от поискового бэкенда: для прод нужен ключ Tavily (бесплатный тариф есть); без ключа поиск деградирует до мусорных кандидатов.

## 7. Поиск связанных постов и генерация текста

1. Эмбеддинг новости → поиск top-3 ближайших **постов канала** (отдельная таблица, туда попадает только опубликованное) за последние Y дней (`context.window_days`, дефолт 14) с порогом сходства (`context.min_similarity`). Для Qwen3-Embedding рекомендуется **0.5**: при пороге 0.7 отфильтровывается ~60% релевантного контекста (результаты бенчмарка RAG).
2. LLM получает: исходную новость, найденные прошлые посты (текст, дата, ссылка t.me/...), системный промпт со **style guide** (тон канала, примеры постов — редактируемый файл `prompts/style.md`), требования:
   - написать пост в стиле канала, а не пересказ источника;
   - если это продолжение прошлой темы — явно об этом написать («Как мы писали ранее…») и дать ссылку на прошлый пост; id ссылки — в `references_post_ids` (рассинхрон «ссылка в тексте, id не указан» недопустим);
   - длина ≤ 1000 символов (лимит caption при фото), HTML-разметка Telegram; ссылка на прошлый пост оборачивает только слова «писали ранее», не целые абзацы;
   - без выдуманных фактов — только то, что есть во входной новости.
3. Результат — structured output: `{text, references_post_ids: [...]}`.
4. Если пост превысил 1000 символов — повторный вызов LLM на сокращение; сокращённый текст принимается только при длине 200–1000 символов, иначе fallback на обрезку оригинала до 1000 символов (`MIN_POST_LENGTH`/`MAX_POST_LENGTH` в `app/generator.py`).

## 8. Публикация

Конфиг `publish.mode`:

- **`auto`** — пост сразу публикуется в канал (фото через `sendMediaGroup`/`sendPhoto`, без фото — `sendMessage`). Rate-limit: не более M постов в час (`publish.max_per_hour`), «тихие часы» (`publish.quiet_hours`), лишние посты в очередь.
- **`moderation`** — черновик (текст + фото) приходит админу (`telegram.admin_id`, см. п. 9) в личку бота с кнопками:
  - **«Опубликовать»** — публикация в канал как есть (фото через `sendMediaGroup`/`sendPhoto`, без фото — `sendMessage`);
  - **«Без фото»** — появляется только если у черновика есть фото; публикует только текст, фото остаются в БД (аудит);
  - **«Редактировать»** — прислать новый текст, фото остаются;
  - **«Отклонить»**.
  Таймаут модерации (дефолт 24ч) → отклонение.
  При отклонении (вручную или по таймауту) черновик удаляется из таблицы `posts`
  (каскадом — вместе с фото и связями), новость получает `status=rejected`.

После публикации: `tg_message_id`, текст и эмбеддинг поста сохраняются в БД постов (участвует в будущих поисках связанных постов).

## 9. Админ-меню и статистика

У бота **один админ**: `telegram.admin_id` (единственный id). Именно он получает посты на модерацию (см. п. 8) и имеет доступ к админ-меню. Апдейты от всех остальных пользователей игнорируются (проверка `from_user.id == admin_id` на каждый апдейт).

- Команда `/admin` открывает инлайн-меню: кнопка «📊 Статистика» и «🔄 Обновить» (пересчёт, редактирование того же сообщения).
- Статистика считается на лету SQL-запросами к `news`/`posts` (отдельных таблиц не требуется):
  - за 24ч / 7 дней / всего: получено новостей, опубликовано, дубликатов, отклонено на модерации, `failed`, `needs_review`;
  - текущее состояние: в обработке (очередь), ждут модерации, в очереди публикации (rate-limit / тихие часы);
  - последний опубликованный пост: `tg_url` + время;
  - по источникам: число новостей по каждому фиду за 24ч.

## 10. Эмулятор новостей (dev-инструмент для тестов)

- Отдельная папка `emulator/` в корне репозитория. К приложению и docker-compose **отношения не имеет**: в docker-образ не включается, в compose не описан, запускается вручную локально (`python emulator/main.py`).
- Назначение: ручное e2e-тестирование пайплайна без реальных СМИ. Локальный HTTP-сервер отдаёт RSS-фид (`GET /rss`), в котором периодически (интервал — CLI-параметр, дефолт 60 сек) появляются новые записи со сгенерированными `title/summary/link/guid/published`. `link` ведёт на страницу-заглушку того же сервера с полным текстом статьи (проверяется и догрузка через trafilatura).
- Сценарии генерации (CLI-параметр `--scenario`):
  - `random` — случайные новости из шаблонов;
  - `duplicates` — те же новости с переформулировкой и новым guid (проверка дедупликации);
  - `developing` — продолжения ранее сгенерированных тем (проверка ссылок на прошлые посты);
  - `mixed` — все сценарии вперемешку.
- Использование: в `rss.feeds` конфига приложения добавляется фид `http://localhost:PORT/rss` (или `http://host.docker.internal:PORT/rss`, если приложение в docker).
- В unit/интеграционных тестах не используется — там моки (см. п. 13); эмулятор — только для ручного прогона.

## 12. Модель данных (PostgreSQL)

Размерность векторов задаётся конфигом `embeddings.dimensions` (`__DIM__` в `app/db/schema.sql`). **Ограничение pgvector: HNSW-индекс не строится для векторов >2000 измерений** — с 4B (2560) и 8B (4096) эмбеддингами `init_schema` упадёт; пути решения — MRL-обрезка вектора до ≤2000 dims (Qwen3-Embedding поддерживает: 8B→1024 dims без потери качества ранжирования) или отказ от HNSW на малых объёмах.

- **news**: id, source (имя фида из конфига), external_id (guid или нормализованный link записи), title, text, url (ссылка на статью), full_text_fetched (bool — удалось ли догрузить полный текст), published_at, embedding vector(__DIM__), status (`pending/dedup/photo_search/writing/moderation/published/duplicate/needs_review/rejected/failed`), duplicate_of_id, created_at. Unique(source, external_id). Индекс HNSW по embedding.
- **posts**: id, news_id, text, embedding vector(__DIM__), tg_message_id, tg_url, status (`draft/queued/published/failed`), published_at (момент публикации, для восстановления rate-limit окна после рестарта), created_at. Индекс HNSW. Отклонённые черновики удаляются (статуса rejected у постов нет).
- **post_images**: id, post_id, source_url, local_path, position.
- **post_references**: post_id, referenced_post_id (для связей «продолжение»).
- **processing_log**: news_id, stage, level, message, created_at — трейс по каждой новости.

## 13. Нефункциональные требования

- Точка входа — `main.py`, запуск только `python main.py` (без `python -m`); то же для эмулятора (`python emulator/main.py`).
- Всё IO асинхронное; ретраи (3x, exp backoff) на LLM/Tavily/Telegram/БД; таймауты на все внешние вызовы (LLM 120с, Tavily 30с).
- Структурированные логи (JSON) с `news_id` сквозь весь пайплайн.
- Падение одного этапа не роняет очередь; необработанные исключения → `status=failed` + лог.
- docker-compose: `app` (демон, без проброшенных портов), `ollama` (профиль optional). PostgreSQL устанавливается на хост-машине (16+, расширение pgvector), из контейнера доступен через `host.docker.internal:5432`.
- Тесты (55, `pytest tests/`): unit — дедупликация (мок LLM/эмбеддингов), парсинг RSS (фикстуры фидов), генератор поста (включая нижнюю границу сокращения), клавиатуры модерации, фото-агент (мок tool-calls, регрессии на параллельные вызовы, изоляция от картинок статьи), textutil, правила публикации; интеграционные — полный пайплайн с моками внешних сервисов, публикация из модерации (в т.ч. «без фото»). Для интеграционных тестов нужен Postgres на машине; DSN берётся из `TEST_DSN` в `.env`.
- Песочница `page_test/` (в git не входит): собранные реальные новости, харнесс tandem-теста (RAG + генерация на OpenCode Go), фото-тест боевого агента, отчёты с рекомендациями по калибровке промптов.

## 14. Критерии приёмки

1. В RSS-фиде появилась новость → в течение `poll_interval` + 2 мин пост (с фото или без) опубликован/отправлен на модерацию.
2. Та же новость с другим `external_id` и переформулированным текстом → определена как дубликат.
3. Новость-продолжение → пост содержит ссылку на прошлый пост канала, id — в `references_post_ids`.
4. Недоступность Tavily/фото не блокирует публикацию текстового поста.
5. Смена `publish.mode` без изменения кода (только конфиг + рестарт сервиса).
6. Команда `/admin` от админа показывает статистику, совпадающую с данными в БД; от чужого id — игнорируется.
7. Фид эмулятора в `rss.feeds` → сгенерированные новости проходят весь пайплайн; сценарий `duplicates` → в БД появляются записи `status=duplicate`, сценарий `developing` → посты содержат ссылки на прошлые посты.
8. Черновик с фото: кнопка «Без фото» публикует только текст; кнопка «Без фото» не показывается у текстовых черновиков.
9. Если точных фото нет, агент ищет тематически близкий кадр; пустой выбор — только когда и тематические кандидаты не подходят.

## 15. Открытые вопросы

Заложены дефолты, легко меняются в конфиге: тематика/стиль канала для `prompts/style.md`, список RSS-фидов, значение X дней для дедупликации (дефолт 3), нужен ли web-дашборд со статусами (пока — нет, статистика в админ-меню бота, п. 9).

Открытые вопросы по итогам тестовых прогонов:

- **Ключ Tavily** (бесплатный тариф) — обязателен для прод-качества поиска фото; без него кандидаты деградируют до мусора (проверено шимом Bing/Openverse).
- **Порог `dedup.min_similarity`** (дефолт 0.75) под Qwen3-Embedding не калибровался — бенчмарк прогонял только контекстный поиск; проверить на реальных дублях.
- **Ресурсная модель прод-сервера** (2 vCPU / 4 GB, CPU-only): 0.6B Q4 — единственная реальная опция эмбеддингов (~1 ГБ RAM, ~7 мс/токен на 2 P-ядрах; длинную новость до 6000 символов считать ~15 с). Рекомендуется снизить `embeddings.max_chars` до ~2000 (эмбеддинг ~3× быстрее, смысл в первых абзацах). Ollama на 2-ядерном сервере сама выставит корректный `num_thread`; на машинах с большим числом ядер ограничивать нагрузки иначе.
- **Расширение админки** (не реализовано): управление фидами из бота, повторная обработка `failed`/`needs_review`, несколько админов, пауза пайплайна.
- **Шлюзы LLM с сессионными заголовками** (OpenCode Go требует `x-opencode-session`): `LLMProvider` пока не поддерживает кастомные заголовки — для таких шлюзов нужен небольшой расшир конфига/клиента.
